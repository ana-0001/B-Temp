# 🌳 مهارة إدارة مستودعات Git/GitHub الاحترافية

> **الهدف:** تحويل تعامل الـ AI مع أي مستودع Git/GitHub من فوضى أسماء عشوائية وcommits غامضة، إلى نظام شجري منظم قابل للتتبع، بتعليقات وcommits ورسائل بالعربية المصرية.

---

## 🧭 المبادئ الأساسية (Override — لا تُنتهك)

```markdown
✅ الكود نفسه (متغيرات/دوال/كلاسات) دايماً بالإنجليزية
✅ كل تعليق (Comment / JSDoc / Docstring) داخل الكود لازم يكون بالعربية المصرية
✅ كل Commit message وPR description وIssue comment لازم يكون بالعربية المصرية
✅ أي فرع جديد لازم ياخد "رقم شجري" (Tree ID) قبل الاسم — مفيش فروع من غير رقم
✅ قبل أي عملية Git خطيرة (push --force, reset --hard, rebase على main) — اسأل المستخدم وأكّد الأول
✅ متعملش commit واحد "كبير" فيه أكتر من هدف — قسّم لcommits ذرية كل واحد بغرض واحد
```

## 1️⃣ نظام الترقيم الشجري للفروع (Branch Tree Numbering)

### 🎯 الفكرة
بدل ما الفروع تتسمى عشوائي زي `feature-login-fix-2` أو `test123`، كل فرع بياخد **رقم موقعه في شجرة المشروع**، بحيث من الاسم بس تقدر تعرف:
- الفرع ده متفرع من أنهي فرع؟
- هو فرع رئيسي ولا فرعي (sub-branch)؟
- ترتيبه بين إخواته إيه؟

### 📐 الصيغة العامة
```
<type>/<tree-id>-<slug-بالإنجليزية>
```

| الجزء | الشرح |
|---|---|
| `type` | نوع الفرع: `feature` / `fix` / `hotfix` / `release` / `chore` / `docs` |
| `tree-id` | الرقم الشجري (مفصول بنقط زي Dewey Decimal) |
| `slug` | اسم مختصر بالإنجليزية يوصف المحتوى (kebab-case) |

### 🌳 مستويات الشجرة
```
main                                 → الجذر (Root) — بدون رقم
 └── develop                         → 1
       ├── release/1.0               → 1.1
       │     ├── feature/1.1.1-login       → أول فرع اتفرّع من release/1.0
       │     ├── feature/1.1.2-signup      → ثاني فرع اتفرّع من نفس الأب
       │     │     └── fix/1.1.2.1-signup-validation   → فرع تصحيح جوه feature
       │     └── fix/1.1.3-payment-bug
       ├── release/2.0               → 1.2  (ثاني فرع release متفرع من develop)
       │     └── feature/1.2.1-dark-mode
       └── chore/1.3-ci-pipeline
 └── hotfix/0.1-critical-security    → متفرع مباشرة من main (بيبدأ بـ 0)
```

### ⚙️ قاعدة توليد الرقم عند إنشاء فرع جديد
1. **الفرع الجديد بياخد رقم أبوه + نقطة + رقم تسلسلي** (أول فرع تحت نفس الأب = `.1`، اللي بعده `.2`، وهكذا).
2. **الفروع المتفرعة مباشرة من `main`** تبدأ بـ `0` (زي hotfix)، أو `1`, `2`, `3`... لو متعددة ومتوازية (زي `develop`).
3. **الفروع المتفرعة من `develop`** تبدأ من `1.1`, `1.2`, `1.3`...
4. **لو رجعت لفرع قديم وفرّعت منه تاني**، الفرع الجديد بياخد الرقم التالي المتاح تحته (متكررش رقم اتاخد قبل كده حتى لو الفرع القديم اتقفل/اتدمج).
5. **قبل أي `git branch` أو `git checkout -b`**، لازم تتأكد من آخر رقم مُستخدم عن طريق `git branch -a` وتفحص الأسماء الموجودة، بعدين تحسب الرقم التالي — مينفعش تخمّن.

### 🧾 أمثلة صحيحة
```bash
git checkout -b feature/1.1.1-login
git checkout -b fix/1.1.2.1-signup-validation
git checkout -b hotfix/0.1-critical-security
git checkout -b release/1.2
```

### ❌ أمثلة ممنوعة
```bash
git checkout -b login-fix          # مفيش نوع ومفيش رقم شجري
git checkout -b feature/2           # رقم من غير سياق (متفرع من إيه؟)
git checkout -b feat_new_thing_v2   # صيغة غير موحّدة
```

## 2️⃣ نظام ترقيم الإصدارات (Release / Tag Tree Numbering)

نفس منطق الشجرة بينطبق على الـ Tags، لكن بصيغة Semantic-like متوافقة مع الشجرة:

```
v<major>.<minor>.<patch>
```

| الجزء | يتغيّر لما... |
|---|---|
| `major` | فيه Breaking Change أو تغيير جذري في البنية |
| `minor` | فيه Feature جديدة (متفرعة كـ `feature/x.y.z-...` واتدمجت) |
| `patch` | فيه Fix أو Hotfix اتدمج |

> **الربط بين الفروع والـ Tags:** لو `feature/1.2.3-dark-mode` اتدمجت في `release/1.2`، والـ release ده هو أول إصدار فعلي، يبقى الـ Tag بيبقى `v1.2.0`. أي Fix بعد كده على نفس الـ release يبقى `v1.2.1`, `v1.2.2`...

### مثال متكامل لمستودع multi-package (Monorepo)
```
packages/
 ├── 1-core/          → الحزمة الأساسية (رقم 1 لأنها الجذر المنطقي)
 ├── 1.1-core-utils/  → فرعية من core
 ├── 2-ui/            → حزمة مستقلة موازية
 └── 2.1-ui-icons/    → فرعية من ui
```

## 3️⃣ التعليقات الإلزامية بالعربية المصرية

### القاعدة الذهبية
```markdown
الكود بالإنجليزية → لكن أي شرح، تعليق، JSDoc، أو رسالة للمستخدم/المطور لازم عربي مصري
```

### مثال JSDoc
```javascript
/**
 * بتجيب بيانات المستخدم من الـ API وتتأكد إن التوكن لسه valid
 * لو التوكن منتهي، بترجع null وتسجّل تحذير في الـ log
 * @param {string} userId - آيدي المستخدم
 * @returns {Promise<User|null>}
 */
async function fetchUser(userId) {
  // بنتأكد الأول إن الآيدي مش فاضي قبل ما نضرب الـ API
  if (!userId) return null;
  // ...
}
```

### مثال تعليق Inline
```python
# بنحسب الإجمالي بعد الخصم — الخصم بيتطبق بس لو فوق 500 جنيه
total = calculate_discount(cart_total)
```

## 4️⃣ صيغة Commit Messages (بالعربية المصرية في الوصف)

### الصيغة
```
<emoji> <type>(<scope>): <عنوان مختصر بالعربي المصري أو الإنجليزي المختصر>

<شرح تفصيلي بالعربية المصرية لو محتاج — إيه اللي اتغير وليه>
```

| Emoji | Type | متى تُستخدم |
|---|---|---|
| ✨ | feat | فيتشر جديدة |
| 🐛 | fix | إصلاح Bug |
| 📝 | docs | توثيق |
| ♻️ | refactor | إعادة هيكلة من غير تغيير سلوك |
| ✅ | test | إضافة/تعديل اختبارات |
| 🔧 | chore | إعدادات/أدوات |
| ⚡ | perf | تحسين أداء |
| 🔒 | security | إصلاح أمني |
| 🗃️ | db | تعديل/Migration في قاعدة البيانات |
| 🏗️ | arch | تغيير معماري |
| 🌳 | branch | إنشاء/دمج فرع جديد في الشجرة |

### مثال كامل
```bash
git commit -m "✨ feat(auth): إضافة تسجيل دخول بجوجل" \
           -m "أضفنا زرار Google OAuth في صفحة اللوجين، وربطناه بالـ backend عن طريق endpoint جديد /auth/google. اتعمل تست يدوي على الفلو كامل واشتغل تمام."
```

### قواعد إلزامية للـ Commit
```markdown
□ commit واحد = تغيير منطقي واحد فقط (Atomic Commit)
□ العنوان مش أطول من 72 حرف
□ لو التغيير معقد أو فيه قرار تقني، اشرحه في الـ body بالعربي المصري
□ ممنوع commits زي "fix" أو "update" أو "تعديلات" من غير تفاصيل
```

## 5️⃣ Pull Requests (قالب إلزامي)

```markdown
## 🎯 الهدف من الـ PR
[شرح بالعربي المصري: إيه المشكلة اللي بنحلها أو الفيتشر اللي بنضيفها]

## 🌳 الفرع
`feature/1.1.1-login` ← متفرع من `release/1.0`

## 📝 التغييرات
- [وصف كل تغيير رئيسي بالعربي المصري]

## ✅ تم الاختبار
- [ ] اشتغل محلياً بدون أخطاء
- [ ] الاختبارات (Tests) عدّت
- [ ] اتعمل مراجعة يدوية للـ Edge Cases

## ⚠️ ملاحظات للمراجع (Reviewer)
[أي حاجة محتاج المراجع ياخد باله منها]
```

### قواعد الـ Merge
```markdown
✅ لازم Squash Merge للـ feature branches الصغيرة عشان الـ history يفضل نضيف
✅ Release branches تتدمج بـ Merge Commit عادي (عشان نحافظ على تاريخ كل commit جواها)
✅ بعد الدمج، امسح الفرع القديم — بس الرقم الشجري بتاعه يفضل "محجوز" ومتترجعش تستخدمه تاني
❌ ممنوع Force Push على main / develop / release/* إلا بعد تأكيد صريح من المستخدم
```

## 6️⃣ التعامل مع Issues على GitHub

- عنوان الـ Issue بالإنجليزية المختصرة (عشان يتوافق مع الأدوات والبحث)، لكن **كل تعليق ورد داخل الـ Issue بالعربي المصري**.
- استخدم Labels موحّدة: `bug`, `feature`, `question`, `needs-triage`, وربطها برقم الفرع اللي هيحل المشكلة لما يتفتح: مثلاً تعليق `هيتحل في fix/1.1.2.1-signup-validation`.

---

## 7️⃣ قائمة الفحص الشاملة (قبل أي Push/PR)

```markdown
□ اسم الفرع متوافق مع نظام الترقيم الشجري؟
□ كل Commit له رسالة واضحة بالعربي المصري في الـ body؟
□ كل تعليق/JSDoc في الكود المُضاف بالعربية المصرية؟
□ الكود نفسه (أسماء المتغيرات/الدوال) بالإنجليزية؟
□ مفيش secrets أو .env اتضاف بالغلط؟
□ تم عمل git status وgit diff --staged للمراجعة قبل الـ commit؟
□ الـ PR فيه القالب كامل (الهدف، الفرع، التغييرات، الاختبار)؟
□ لو فيه عملية خطيرة (force push / rebase على فرع مشترك) — تم تأكيدها مع المستخدم؟
```

## 🚫 الممنوعات (بدون استثناء)

```markdown
❌ إنشاء فرع بدون رقم شجري أو بدون type بادئ
❌ Commit واحد فيه أكتر من غرض (مثلاً feature + fix + refactor في نفس الـ commit)
❌ تعليقات كود بالإنجليزية أو "Arabizi" (عربي بحروف إنجليزية)
❌ استخدام git push --force على main/develop/release بدون تأكيد صريح من المستخدم
❌ حذف أو إعادة استخدام رقم شجري اتاخد قبل كده لفرع مختلف
❌ commit messages غامضة زي "fix", "update", "changes", "تعديل"
```
